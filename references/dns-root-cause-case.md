# DNS 根因实战案例（间歇性 11 秒卡顿）

> 一份真实排查记录，作为本技能的「标准动作」样例。环境：Windows 11 + WiFi，用户反映「有时点开网页要等很久」。本案例只排查**非代理直连路径**。

## 症状

- 用户称：网页有时打开很慢、转圈很久；关掉代理（Clash）不用时也慢。
- 说明：本案例只排查直连路径（非代理路径）。

## 排查过程（全部只读）

1. **物理层健康**：`netsh wlan show interfaces` Signal=81%；网关 `192.168.1.1` 延迟 2–3ms → 本地链路正常。
2. **直连 vs 代理耗时**：`curl --noproxy '*'` 开 baidu 曾达 **11.3s**，`curl -x http://127.0.0.1:7897` 仅 1.5s → 直连路径坏；但代理开着时反而快（说明代理不是原因，只是护住了 DNS 环节）。
3. **抓慢事件并定位**：多轮 `curl -4 --noproxy '*' -w "nl=%{time_namelookup} ct=%{time_connect} st=%{time_starttransfer} tt=%{time_total}"`：
   `baidu #1  nl=11.086766  ct=11.118662  st=11.184887  tt=11.185000`
   → **整段 11 秒 100% 卡在 `nl`（DNS 解析）**，建连/首字节都在 DNS 回来后瞬间完成。
4. **路由器 DNS 稳定性**：多次 `Resolve-DnsName www.baidu.com -Server 192.168.1.1` → 冷查询 832ms，热缓存 7–8ms（说明平时慢是因为缓存失效后的慢解析）。
5. **公共 DNS 对照**：`Resolve-DnsName ... -Server 223.5.5.5` 稳定 25–31ms；`119.29.29.29` 26ms；`8.8.8.8` 50ms → 公共 DNS 始终快。
6. **排除项**：WLAN 接收速率仅 22KB/s（无后台占带宽）；IPv6 直连 baidu 0.1s（IPv6 回退排除）；网关/WiFi 健康（排除链路）；DNS 回来后首字节 66ms（排除服务器）。

## 根因（已查实，非推测）

WLAN 的 DNS 服务器是路由器 `192.168.1.1`（DHCP 默认继承），而**路由器自带的 DNS 转发器/上游（运营商 DNS）极不稳定**，冷查询要 800ms–11s。这是路由器默认行为，不是用户手动改坏——`netsh` 证实为 `configured through DHCP`，虚拟机安装只动了虚拟网卡 VMnet8（设了静态 8.8.8.8），未碰 WLAN。

## 修复（用户同意后执行，需管理员权限）

将 WLAN 的 DNS 改为 `223.5.5.5`（首选）/ `119.29.29.29`（备用）。

> 任何设置改动都需用户明确同意；改 DNS 需要管理员权限（UAC）。本技能只诊断，不擅自修改。

## 验证（修复后只读确认）

- `netsh interface ip show dns "WLAN"` → `Statically Configured DNS Servers: 223.5.5.5 / 119.29.29.29`。
- 直连多站点 `curl -4 --noproxy '*' -w`：所有 `nl`（DNS）降到 **7–29ms**，整页 0.1–0.35s，11 秒卡顿消失。

## 本案例印证的方法论

- 只读优先、分层定位；用 `curl -w` 的 `nl` 字段把「慢」精确归因到 DNS。
- 对照实验（当前 DNS vs 公共 DNS）确凿锁定根因，而非「可能」。
- 明确边界：代理不是原因（开代理反而快）。
